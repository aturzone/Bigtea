# LTS 0.0.0 — "run a huge model on your own machine, without knowing why it works"

The product Atur described: a user installs Bigtea on any OS, asks for a model, and it picks
the right quant for their hardware, downloads it, configures itself, and runs — fast enough to
code against.

This epic is the gap between that and what exists. **What exists today** (2026-08-07): a
verified V4-Flash *prefill* on Windows, driven by a hand-typed path to shard 1, at 0.14 tok/s,
with no generation, no downloader, and no tested build on Linux or macOS.

Nothing here is research. Every ticket is engineering with a known shape.

---

## T0 — GATE: generation exists and beats llama.cpp

**Nothing else in this epic is worth shipping without this.** An LTS that prefills and cannot
generate is not a runner, and "faster than llama.cpp" is a *generation* claim — their 0.45
tok/s is a generation number we currently cannot contest at all.

- **T0.1** Kill the copies. `read_at` fills a caller-owned buffer instead of returning a fresh
  `Vec`; the expert path reads each slice directly into its final position in the compact
  stack. Measure `read_exact_at` alone against `read_at` **first** — if the copy is not the
  gap, do not make the API change. See `v4flash-speed-budget.md`.
- **T0.2** Residency: load the always-read set once, not per block. Bounded by RAM; probe
  already reports what must be closed.
- **T0.3** The generation loop: persistent compressor ring (prefill can skip it, generation
  cannot), a KV cache that grows rather than being rebuilt, and `stream.rs`'s expert cache.
- **T0.4** Measure against llama.cpp on the same machine and prompt, both engines, command
  lines pasted into the head-to-head node. **If we do not win, say so and do not ship the
  claim.**

**Exit:** V4-Flash generates correct text, measured, faster than 0.45 tok/s.

## T1 — One command, any OS

- **T1.1** Build on Linux and macOS. Today only the Windows GNU toolchain + MSYS2 path is
  exercised; `bigtea-io`'s direct-I/O flags are per-platform (`FILE_FLAG_NO_BUFFERING`,
  `O_DIRECT`, `F_NOCACHE`) and only one is tested. CI on three runners.
- **T1.2** Ship binaries, not a build. A user must not need Rust, MSYS2, or a ggml checkout.
  Static-link ggml; publish per-platform archives on GitHub Releases.
- **T1.3** `bigtea run <model>` as the primary verb, where `<model>` is a *name*, not a path to
  shard 1 of 5.

---

## T2 — The model catalogue

**Models live on Hugging Face, not GitHub.** GitHub carries the code and the releases; the
weights are HF repos, and for V4-Flash specifically an Unsloth dynamic quant split across five
shards. The downloader must speak the HF API.

- **T2.1** A catalogue mapping a short name to an HF repo, its quant variants, their sizes, and
  their shard layout. Checked into the repo so it is reviewable and versioned, not fetched from
  a server we would then have to run.
- **T2.2** `bigtea pull <model>` — resolve, resume interrupted downloads, verify checksums,
  handle multi-shard sets as one unit. A 144 GB download **will** be interrupted; resume is not
  optional.
- **T2.3** Honour `HF_TOKEN` for gated repos, and say plainly when a model needs one rather
  than failing with a 401.
- **T2.4** Disk-space check *before* starting. 144 GB half-downloaded is a bad afternoon.

---

## T3 — Choose the right quant for this machine

This is where Bigtea has something no other runner does: `bigtea-probe` and
`bigtea-model-info` already measure RAM, disk bandwidth and the resident/streamed split, and
already predict tok/s at a stated footprint.

- **T3.1** `bigtea pull <model>` with no quant specified picks one from the probe: the largest
  quant whose *always-read* set fits the machine's usable RAM, since that is what decides
  whether the design works at all.
- **T3.2** Say the prediction out loud before downloading 144 GB — "on this machine, ~0.7
  tok/s, 7.4 GiB resident, 137 GiB streamed" — and let the user decline.
- **T3.3** Refuse, with a reason, when nothing fits. A model that will thrash is worse than a
  model that will not start.

---

## T4 — Configure itself

- **T4.1** Derive the prefill block, expert-cache budget and thread count from the probe
  instead of the current fixed defaults. Block size is worth more than any kernel here
  (512 → 4096 was 30.5 → 43.6 tok/s).
- **T4.2** Pick the I/O mode from the model-size-to-RAM ratio. Bypassing the page cache is
  right when the model dwarfs RAM and **wrong when it nearly fits** — there the kernel's
  elastic cache beats a fixed budget, which is why Bigtea loses to llama.cpp on Qwen3
  generation.
- **T4.3** Every derived value overridable by a flag, and printed at startup so a bad
  auto-choice is visible rather than mysterious.

---

## T5 — The interface

- **T5.1** A REPL worth using: streaming output, `Ctrl-C` that stops generation rather than the
  process, and a progress line during the minutes-long first load.
- **T5.2** An OpenAI-compatible `/v1/chat/completions` server. **This is what makes it usable
  from a coding agent** and it is the single highest-leverage item in T5 — every existing
  editor integration speaks that shape already.
- **T5.3** Show what the engine is doing: resident GiB, expert cache hit rate, tok/s, bytes
  read per token. This project's own history says hit rate is not a success metric on its own,
  so display it *next to* tok/s and footprint, never instead of them.

---

## What LTS 0.0.0 will honestly claim

Written now, before the work, so it cannot drift:

- Runs models several times larger than RAM, on CPU, on three operating systems.
- On DeepSeek-V4-Flash it is **faster than llama.cpp**, with the gap widening at long context
  because their dense weights get evicted by cold expert traffic and ours do not.
- It tells you what it will do before it does it, and refuses when it will not work.

**It will not claim** to make a 144 GB model fast on a laptop. On this hardware 3.21 GiB of
experts per token over a 2.55 GB/s disk is ~1.35 s/token, and the honest laptop number is
low single-digit tok/s. The same binary on a workstation that fits the model in RAM is a
different story — and *that* is the product: one engine that degrades gracefully instead of
refusing to start.
