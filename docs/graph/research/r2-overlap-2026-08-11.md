Block N+1's always-read weights are read **while block N computes**. Measured on
V4-Flash with 3.10 GiB of the always-read set still streaming: **1.07x prefill,
1.13x generation**, and the dense read all but disappears.

The 2026-08-08 scoping put the ceiling at ~1.4x. This gets a third of it, and
the measurement says exactly where the rest went.

## The result

Four runs, one session, free RAM matched to within 0.03 GiB — which matters,
because it is the axis V4-Flash numbers drift along:

| | free RAM | prefill | generation | dense read | expert read |
|---|---:|---:|---:|---:|---:|
| overlap off | 7.10 GiB | 0.56 tok/s | 0.280 tok/s | **2.15 s** | 7.01 s |
| overlap on | 7.13 | **0.60** | **0.316** | **0.02 s** | 8.13 s |
| overlap on, repeat | 7.11 | **0.60** | **0.317** | 0.02 s | 8.21 s |

```
bigtea-run DeepSeek-V4-Flash-UD-Q4_K_XL-00001-of-00005.gguf \
           "The capital of France is" -n 2       # BIGTEA_BLOCK_TIMING=1
resident   loaded 104 tensors, 4.27 GiB of 4.27 GiB budget;
           3.10 GiB did not fit and will be re-read every token
```

The two on-runs land on 0.316 and 0.317, so this is reproducible rather than a
lucky sample.

## Why it is only a third of the ceiling

**The dense read is completely hidden — 2.15 s to 0.02 s, over 86 block-passes.**
That part worked exactly as designed. But the expert reads got **1.16 s slower**,
and that is where two thirds of the win went.

The obvious explanation is the reader-handle split, and it is wrong. Handing the
prefetch two handles against four changes nothing:

| prefetch readers | dense | expert |
|---:|---:|---:|
| 0 (off) | 2.56 s | 7.02 s |
| 2 | 0.02 s | 8.39 s |
| 4 | 0.04 s | 8.43 s |

**Two hide the dense read as completely as four, and four cost the experts no
more than two.** So the toll is not the pool split — it is the *drive*. Both
sets of reads are competing for the same finite bandwidth, and moving bytes off
the critical path does not make them free. Two is therefore the default: same
benefit, smallest share taken from the foreground.

This is the same lesson as `the-plateau-was-ours-2026-08-10.md` read from the
other side. There, the plateau was ours and the drive had more to give. Here the
drive is genuinely the limit, and overlap only re-sequences the queue.

## The constraint that had to be handled first

`read_range_into_via` requires concurrent readers to pass **distinct** slots — a
synchronous handle is serialised by the OS, so two threads on one hold the drive
at queue depth 1. That is the bug whose fix was worth 1.32x on expert reads.

`READER_HANDLES` is 8 and `read_expert_slices` already fanned out over all
eight, so a prefetch thread started naively would have reused slots the
foreground was using and **reintroduced that bug by hand** — surfacing not as an
error but as "overlap does not help". The pool is partitioned instead:
foreground `0..6`, prefetch `6..8`.

## Why this is exact and not speculative

Routing is data-dependent: block N+1's *experts* are chosen from block N's
output, so they cannot be known before block N runs. Its **dense** tensors do
not depend on routing at all. So nothing here is a guess — a prefetch is never
wrong, only occasionally wasted, and `bind_dense` reads anything the map is
missing.

That also bounds the win: this is R2.1/R2.2 of the original scoping, not R2.3.
The routed experts are 76% of a token's bytes and are untouched.

## Off when it cannot help, not merely idle

With the always-read set fully resident there is nothing to prefetch — and
shrinking the foreground pool anyway would be a **pure loss**, handing two
handles to a thread that reads nothing. So the decision is made once per pass
from whether block 1 has any non-resident tensor, and when there is no shortfall
the overlap is switched off entirely and the expert reads keep all eight.

Block 1 rather than a global "was anything skipped": residency fills
largest-first over the whole model, so a global shortfall can be true while
every block a pass touches is resident. Block 0 is the wrong probe because it
also carries `token_embd`.

## Cost

One extra block's dense tensors held in flight (~147 MiB when nothing is
resident) while the previous block computes. On a machine already short of RAM
that byte competes with residency — the same trade the expert cache lost — which
is the other reason the overlap turns itself off when residency is satisfied.

A prefetch that fails falls back to reading inside `block`; losing the
optimisation is the right failure and it cannot end a run. A *panic* is
re-raised rather than swallowed, because that would be a bug and not a slow disk.

## Verification

All 21 container-backed V4-Flash tests pass with the overlap active, including
the element-sum comparisons against llama.cpp and the cached-step equivalence.
The overlap changes when bytes are read, never which bytes, so a changed output
would have meant a real fault.
