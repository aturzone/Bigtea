## Findings

### Prior art (what to copy, what's missing)
- **llama-bench**: test types `pp(N)`/`tg(N)`/`pg(N,M)` (prompt-processing / text-gen / combined); `-r` repeats (commonly 5) averaged, reports mean **and stddev**; warmup runs by default (`--no-warmup` to disable); output formats md/csv/**json/jsonl/sql**; row fields include build commit, CPU/GPU info, backend, batch size, threads, `n_gpu_layers`, K/V cache type, and MoE-aware flags (`--n-cpu-moe`, `--numa`). https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md
  - Copy: repeat+stddev by default, machine-readable JSON/SQL rows with build+hardware metadata baked in.
  - Missing: no TTFT (pp/tg are throughput-only, not end-to-end request latency), no cache-hit concept, no cold-vs-warm distinction, single-request only (no concurrency).
- **llama.cpp server bench** (`tools/server/bench/speed-bench`): hits the OpenAI-compatible endpoint and reads the server's own per-request timing fields — `avg_prompt_t/s` from `timings.prompt_per_second`, `avg_pred_t/s` from `timings.predicted_per_second` — plus `avg_latency` (client-observed e2e); sample volume via `--limit`, no explicit repeat-count/CI; JSON output has `config`/`selected_samples`/`completed_samples`/`failed_samples`/`summary`/`results`. A separate k6-based load tool sweeps concurrent virtual users (needs `xk6-sse` for streaming). https://github.com/ggml-org/llama.cpp/blob/master/tools/server/bench/speed-bench/README.md , https://deepwiki.com/qualcomm/llama.cpp/7.2-benchmarking-and-evaluation-tools
  - Copy: reading tok/s from the engine's own reported timings, not client-side wall-clock (avoids HTTP/JSON jitter contaminating the number).
  - Missing: no statistical rigor (no repeats/CI), no MoE/cache signal.
- **vLLM `vllm bench serve`**: defines **TTFT**, **TPOT** (per-output-token latency excluding the first), **ITL** (inter-token latency), **e2el** (end-to-end); reports mean/median/**p99** (configurable `--metric-percentiles`, default 99) for `--percentile-metrics` (default `ttft,tpot,itl`); load shape via `--request-rate` (default `inf` = burst all at t0) with Poisson or gamma (`--burstiness`) arrival and an independent `--max-concurrency` cap; `--num-prompts` default 1000; `--num-warmups` default **0** (must be set explicitly — a footgun); built-in prompt-distribution generators for reproducibility: `random` (default 1024 in/128 out tokens), `sharegpt` (real conversational lengths), `sonnet` (fixed 550 in/150 out/200 prefix); `--save-result`/`--save-detailed` for JSON. https://docs.vllm.ai/en/latest/cli/bench/serve/
  - Copy almost wholesale: TTFT/TPOT/ITL/e2el terminology (already the de facto industry standard, used in NVIDIA/Red Hat docs too), percentile reporting (not just mean), standardized synthetic+real prompt sets, controllable arrival process for realistic bursty load.
  - Missing: single-engine focus, no offload-tier or MoE-cache awareness, warmup opt-in not opt-out.
- **MLPerf Inference**: LoadGen-driven; 4 scenarios — Single-Stream, Multi-Stream, Server (Poisson arrivals, p99 latency-bounded), Offline (throughput-only, min 600s runtime); minimum query count/duration per scenario is *derived* from the target tail-latency percentile + margin + desired confidence interval (formula-driven, not a fixed guess); Server-scenario runs are INVALID if measured QPS < declared target QPS at the p99 bound; submission rules require fixed random seeds, disabled dynamic batching, fixed/locked clocks. Hardware fingerprint lives in `<system_desc_id>.json`: `host_memory_capacity`, `host_processor_core_count/frequency/model_name`, `host_processors_per_node`, `host_storage_capacity/type`, `accelerator_model_name/memory_capacity/frequency/interconnect`, `accelerators_per_node`, `framework`, `operating_system`. https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc , https://docs.mlcommons.org/inference/submission/
  - Copy: scenario taxonomy maps directly onto our use cases (Single-Stream ≈ solo chat user, Server ≈ small-team serving); the system-description JSON as a hardware-fingerprint template; deriving sample count from observed variance + target CI instead of a hardcoded repeat count.
  - Missing: built for datacenter accelerators + accuracy-validated fixed models, no MoE-offload/SSD-tier concept, no expert-cache notion at all, compliance process far heavier than a community tool needs.
- **MLPerf Client** (mlcommons/mlperf_client): closest prior art *in spirit* — a Windows/Linux/macOS client-form-factor ML benchmark with per-scenario `WarmUp`, `Iterations`, and `Delay`-between-iterations config knobs — but its public README does not document TTFT/tok-s metric definitions or an explicit hardware-fingerprint schema, so it's less transparent/reusable than vLLM or MLPerf-datacenter docs for our purposes. https://github.com/mlcommons/mlperf_client
- **LocalScore** (Mozilla Builders, built on llamafile): 3 raw metrics — prompt-processing tok/s, generation tok/s, TTFT — rolled into one composite score (1000=excellent, 250=passable, <100=poor); runs a standardized matrix of 8 scenarios sweeping prompt length 16–4096 and generation length 16–3072 tokens; auto-captures OS name/version, CPU name/arch, RAM capacity, GPU name/manufacturer/VRAM as a lightweight consumer-friendly hardware fingerprint; publishes to a public leaderboard (localscore.ai) searchable by GPU model. https://www.localscore.ai/about , https://www.localscore.ai/
  - Gap worth avoiding: repeat count, warmup procedure, and the exact composite-score formula are **not publicly documented** on the about page (would require reading CLI source) — a transparency gap our own harness should not repeat.
  - Missing: no MoE/cache-hit awareness, no cold-vs-warm protocol.
- **Bench360** (Stuhlmann/Fadel Argerich/Fürst, ZHAW/UPM Madrid, arXiv 2511.16682): multi-engine framework (single-stream/batch/server scenarios) tracking task quality (ROUGE/F1/accuracy) *alongside* system metrics (latency, throughput, energy, startup time) across models/quant levels/engines; demonstrated on 3 GPUs × 4 engines × 4 tasks. https://arxiv.org/abs/2511.16682 — closest academic analog to "harness that validates a predictor + lets users publish comparable results," but datacenter-GPU-oriented, not MoE-CPU-offload-specific, no cache-hit metric.
- **Watt Counts** (arXiv 2604.09048): rigorous LLM-inference energy/perf reproducibility protocol — copy almost wholesale for thermal/steady-state handling (see Reproducibility protocol below).

### Metric definitions
- **Decode tok/s (tg) vs prefill tok/s (pp) must stay separate**, never blended into one number: llama-bench's `pp(N)`/`tg(N)` split exists because prefill is compute-bound and decode is memory-bandwidth-bound (consistent with the roofline model in hardware-profiling.md) — they scale with different hardware ceilings, so a merged "tokens/sec" hides which regime a build/config is in. https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md
- **TTFT**: wall-clock from request submission to first emitted token (includes full prefill + queueing/scheduling latency). Industry-standard term via vLLM/NVIDIA/Red Hat docs. https://docs.vllm.ai/en/latest/cli/bench/serve/
- **TPOT / ITL**: per-token decode latency excluding the first token (mean spacing between tokens 2..N); vLLM tracks both names as effectively the same concept. Report **percentiles (p50/p90/p99)**, not just mean — tail latency is the "stutter" users actually feel. https://docs.vllm.ai/en/latest/cli/bench/serve/
- **e2el**: full request latency = TTFT + sum of all TPOTs; useful as a total sanity check, not a substitute for the split metrics.
- llama.cpp server's per-request response fields `timings.prompt_per_second` / `timings.predicted_per_second` are the authoritative source for pp/tg numbers when benchmarking through the server API (vs. client-side wall-clock, which picks up HTTP/JSON overhead as noise). https://github.com/ggml-org/llama.cpp/blob/master/tools/server/bench/speed-bench/README.md
- **MoE expert-cache-hit-rate** — neither engine exposes this natively (confirmed in ktransformers-vs-llamacpp-moe-offload-gaps.md's "common to both" section: no per-expert activation/cache metric in llama.cpp `/metrics` or ktransformers' balance_serve docs). The most concrete usable definition found is informal, from a llama.cpp feature-request's Python PoC (issue #20757): a **hit** = the expert weight needed by the current token's router decision is already GPU-resident ("zero copies"); a **miss** = it must be copied from pinned RAM (tier 2) or demand-paged from SSD (tier 3). This is countable with two counters (hits, misses) incremented at the offload dispatch point; `hit_rate = hits / (hits + misses)`, trackable per-layer or aggregated. The PoC's measured curve is a useful reference shape for cold→warm behavior: cold start (tokens 0–80): 1.9–2.5 tok/s at 48–56% hit rate; warming (80–160 tokens): 2.6–5.1 tok/s at 53–78%; steady state (160+ tokens): 12–14 tok/s at ~98–100% hit rate; vs. 0.5–1 tok/s with no cache at all. https://github.com/ggml-org/llama.cpp/issues/20757
- Expert-routing skew is *why* a hit-rate metric is meaningful at all: real-world MoE routing is commonly described as skewed so that roughly 15–20% of experts handle ~80% of tokens per layer, which is what makes a small GPU-resident hot-expert cache effective (community-repeated estimate, cross-consistent with the #20757 numbers above, but not independently primary-sourced here — lower confidence, state as an assumption).
- A cache-hit-rate metric should be reported **as a function of token position** (e.g., hit-rate at token 50 vs. token 500), not as one aggregate number — the #20757 data shows it is non-stationary within a single generation (cold→warm→steady); an aggregate over a short run just measures how much of the run was still warming up.

### Reproducibility protocol
- **Warmup**: llama-bench warms up by default (`--no-warmup` to opt out); vLLM's `--num-warmups` defaults to **0** (opt-in — a footgun); MLPerf Client uses a per-scenario `WarmUp` knob. Recommendation: default warmup **on**, not opt-in.
- **Repeats + statistics**: llama-bench repeats N times (commonly 5) and reports mean+stddev. Watt Counts (arXiv 2604.09048) is the most rigorous LLM-specific protocol found:
  - 5 independent iterations per configuration.
  - Steady-state gate *before* each measurement starts: GPU power draw stable within a **3W band for ≥30s** AND GPU temp **<65°C** (thermal throttling typically starts ~75°C, so this leaves headroom); 5-minute safety timeout if it never stabilizes.
  - Power sampled at **10Hz** — validated to give <1% integrated-energy error vs. 200Hz sampling, with <0.5% runtime overhead from the sampling itself.
  - Fixed decode params across all runs (temperature=0, top_k=0, top_p=1, max_gen_len=256, repetition_penalty=1) and fixed random seeds (Python/NumPy/PyTorch), so token-count variance doesn't confound timing variance.
  - Server-scenario runs sustained 5 minutes each — empirically shown to yield energy measurements within **<2% deviation at 95% CI**.
  - https://arxiv.org/html/2604.09048v1
- MLPerf's principle worth copying even without the exact formula: **derive minimum sample count from observed variance + target CI**, not a fixed "always run 5x" guess; Offline scenario still floors at ≥600s regardless. https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc
- **Cold vs. warm cache protocol for MoE/SSD-resident weights**: llama.cpp's `--mmap` loading means "cold" vs "warm" is actually determined by the **OS page cache**, not an explicit engine-level cache — first load after a reboot/cache-drop faults pages in from SSD; a subsequent run with the same weights still in RAM's page cache is "warm" even with no persistent expert-GPU-cache feature at all. A reproducible MoE benchmark needs an explicit, stated step per run: either drop OS caches before a "cold" run (Linux: `echo 3 > /proc/sys/vm/drop_caches`; no confirmed clean Windows equivalent found — see Open questions) or deliberately evict the model by reading enough unrelated data, and must record which state (cold/warm) each result used. https://github.com/ggml-org/llama.cpp/discussions/19163 , https://gist.github.com/DocShotgun/a02a4c0c0a57e43ff4f038b46ca66ae0
- **Prompt/context standardization**: vLLM ships exactly this — `random` (configurable in/out token counts, default 1024/128), `sharegpt` (real conversational distribution), `sonnet` (fixed 550 in/150 out/200 prefix) — so different tools/runs compare on identical input distributions instead of each harness inventing its own. Reuse this rather than a bespoke prompt set. https://docs.vllm.ai/en/latest/cli/bench/serve/
- **Quant format / thermal / power-plan effects on consumer hardware**: no single primary source combines "consumer Windows box + quant format" directly, but Watt Counts' steady-temp/power gate + fixed decode params generalizes directly. Separately: NVIDIA Control Panel's default "Optimal Power" mode is documented to throttle GPU clocks down under intermittent utilization — a reproducible consumer protocol should instruct setting "Prefer Maximum Performance" (and OS power plan = High Performance, not Balanced/Power-saver) before benchmarking, and record which was set in the fingerprint (community-sourced guidance, not a primary spec — lower confidence but directly actionable). Quant format itself (Q4_K_M vs Q8_0 vs FP16 etc.) must be recorded as a first-class fingerprint field since it directly changes both bytes/param (decode speed) and accuracy — never compare tok/s across quant formats without labeling them.

### Result format + variance thresholds
- **Machine-readable schema skeleton**: llama-bench's JSON/JSONL/SQL output already bakes build commit, CPU/GPU/backend, batch size, threads, `n_gpu_layers`, K/V cache type, test type, and ns/tok-per-sec+stddev into one row — a good starting per-run schema shape. https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md
- **Hardware fingerprint**: MLPerf's `system_desc_id.json` is the most complete prior-art template — `submitter/system_name/division/status/number_of_nodes`, `host_memory_capacity`, `host_processor_core_count/frequency/model_name`, `host_processors_per_node`, `host_storage_capacity/type`, `accelerator_model_name/memory_capacity/frequency/host_interconnect/interconnect`, `accelerators_per_node`, `framework`, `operating_system`, `other_software_stack`. https://docs.mlcommons.org/inference/submission/ — extend it with the RAM-bandwidth (STREAM Triad MB/s) and SSD-4K-randread (fio IOPS) numbers already defined as probe outputs in hardware-profiling.md, since MLPerf's datacenter-oriented schema doesn't need those but consumer MoE-offload absolutely does.
- LocalScore's lighter fingerprint (OS name/version/release, CPU name/arch, RAM capacity, GPU name/manufacturer/VRAM) is a validated-at-leaderboard-scale minimum-viable alternative if MLPerf's schema is judged too heavy for a community tool. https://www.localscore.ai/about
- **Variance / "reproducible enough" threshold**: general software-performance-benchmarking guidance puts **5% CV (stddev/mean)** as the accept/investigate line, with ≥5 repeats recommended and ≥10 runs at <5% CV considered defensible for release-gating decisions. DAWNBench's own analysis (arXiv 1806.01427) found ~14% CV was the point at which two systems' time-to-accuracy numbers became reliably distinguishable — i.e., the "distinguishable" threshold is relative to how close the two things being compared are, not an absolute constant. Watt Counts' tighter **<2% (95% CI)** applies specifically to their 5-minute *energy* measurement, achieved only after the full thermal/power steady-state gate — i.e., tighter reproducibility is achievable on the same class of hardware, but requires the full protocol (steady-state gating + fixed seeds + fixed decode params), not just "run it more times."
- **Recommendation for this project**: adopt 5% CV across ≥5 repeats as the default "reproducible enough" bar for tok/s and TTFT on consumer hardware without a thermal-steady-state gate; document that implementing the full Watt-Counts-style steady-state gate should tighten this toward ~2%, and flag results that exceed 5% CV as "noisy — investigate before publishing" rather than silently averaging them into a leaderboard number.
- Sources: https://dzone.com/articles/understanding-the-power-of-coefficient-of-variatio (5% guidance), https://arxiv.org/pdf/1806.01427 (DAWNBench, 14% distinguishability figure), https://arxiv.org/html/2604.09048v1 (Watt Counts, <2%/95%CI).

## Open questions
- No primary source defines a standardized MoE expert-cache-hit-rate metric name/formula as an accepted convention — only the one llama.cpp GitHub issue's informal PoC definition exists. We would be naming/formalizing this metric ourselves, not adopting prior art.
- No confirmed Windows-native equivalent to `echo 3 > /proc/sys/vm/drop_caches` for forcing a genuinely cold page-cache state before a "cold" MoE run — candidate is Sysinternals RAMMap's "Empty Standby List" action, but this was not verified in this pass.
- MLPerf's exact formula for deriving minimum query count from target percentile/margin/CI was referenced only in principle here; the precise equation would need a direct read of `inference_rules.adoc`'s LoadGen section.
- LocalScore's exact composite-score formula and its repeat/warmup counts are not published on its about page; confirming them would require reading the `localscore-cli` source on GitHub (not fetched in this pass).
- Whether a "Prefer Maximum Performance" / High-Performance-power-plan instruction is sufficient on its own for consumer-hardware reproducibility, or whether a Watt-Counts-style temperature/power steady-state gate is actually necessary even for tok/s-only (non-energy) benchmarking, is untested here — worth a small empirical check before finalizing the harness's default protocol.
