## Findings

### Probing (what to measure, how, cross-platform)
- **RAM bandwidth**: STREAM (Triad kernel) is the standard portable measure — C source, Linux/Windows/Mac, reports MB/s for copy/scale/add/triad, NUMA-aware variant exists for multi-socket boxes. https://www.cs.virginia.edu/stream/ref.html
  - Real sustained bandwidth is 70–90% of theoretical/JEDEC spec (controller overhead, refresh cycles): e.g. DDR5-6000 dual-channel theoretical 96GB/s, real STREAM ≈72GB/s (75%). https://bottleneckcalculator.to/en/blog/ddr5-vs-ddr4-real-world-performance-differences/
  - `sysbench memory` is a lighter Linux-only alternative (`sysbench memory --memory-block-size=1M --memory-total-size=8G --memory-oper=write run`), easier to ship/package but less rigorous than STREAM. https://www.binarytides.com/benchmark-ram-speed-on-linux-with-sysbench/
  - Intel MLC gives bandwidth + latency (`max_bandwidth`, `loaded_latency`, `peak_injection_bandwidth` sub-tests), best for NUMA/server accuracy but requires accepting an Intel license to download — friction for a lightweight installer probe. https://www.intel.com/content/www/us/en/download/736633/intel-memory-latency-checker-intel-mlc.html
  - For a <1 min budget: run STREAM Triad alone for ~15–20s with array size ≫ last-level cache (e.g. 4x LLC) — this is what quick benchmarks do to fit a time budget while still avoiding cache-inflated numbers.
- **GPU/VRAM capacity** (fast, <5s, no compute needed): `nvidia-smi --query-gpu=memory.total,memory.free --format=csv` (NVIDIA); Windows-generic via DXGI `IDXGIAdapter3::QueryVideoMemoryInfo` (works for AMD/Intel/NVIDIA dedicated adapters). https://asawicki.info/news_1695_there_is_a_way_to_query_gpu_memory_usage_in_vulkan_-_use_dxgi.html
  - Linux without vendor CLI: read sysfs directly (e.g. amdgpu `mem_info_vram_total`). https://lunnova.dev/articles/linux-get-gpu-vram-size/
  - Vulkan `vkGetPhysicalDeviceMemoryProperties` is the only true cross-vendor/cross-OS API but is "heavy" — opens device nodes, forces GPUs out of low-power states; only worth it if the host tool already links Vulkan for inference itself. https://asawicki.info/news_1695_there_is_a_way_to_query_gpu_memory_usage_in_vulkan_-_use_dxgi.html
- **GPU/VRAM bandwidth** (actual measurement, not just capacity): needs a real copy microbenchmark. NVIDIA's old `bandwidthTest` CUDA sample was removed in CUDA Samples 12.9+; replaced by `nvbandwidth` (H2D/D2H/D2D via copy-engine or kernel-copy). https://github.com/NVIDIA/nvbandwidth , https://developer.nvidia.com/blog/nvidia-nvbandwidth-your-essential-tool-for-measuring-gpu-interconnect-and-memory-performance/
  - For a <1 min preflight this is disproportionate: build/CUDA-toolkit dependency for one number. Practical shortcut — look up published spec-sheet bandwidth (bus width × clock) keyed off the GPU model string already returned by `nvidia-smi`/DXGI; consumer GPU spec numbers are public and reliable, so measuring is low-value here vs. RAM/SSD where real-world variance is much higher.
- **SSD 4K random read**: fio is the standard cross-platform tool (ships as static binary for Windows too, `windowsaio` ioengine). Canonical quick command: `fio --randrepeat=1 --ioengine=libaio --direct=1 --gtod_reduce=1 --name=test --filename=test --bs=4k --iodepth=64 --size=4G --readwrite=randread`. https://github.com/axboe/fio/blob/master/examples/ssd-test.fio
  - `--direct=1` is mandatory to bypass page cache for a true device number; for <1 min budget shrink to 1–2GB test file, runtime 10–15s, iodepth 32–64.
  - Windows-native alternatives: Microsoft's DiskSpd (precise, controllable block size/QD/RW-mix, MS-recommended for "trustworthy numbers"); built-in `winsat disk` formal assessment is coarser — outputs an aggregated score, not raw IOPS/latency, "doesn't map 1:1 with modern NVMe marketing numbers," and isn't queue-depth-controllable, so it under-reports real NVMe random-read ceilings. https://learn.microsoft.com/en-us/windows/win32/winsat/using-winsat , https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/cc742157(v=ws.11)
  - Must run against the actual target install drive, not assumed to be the OS drive — consumer boxes commonly pair a fast NVMe boot drive with a slower secondary/external drive used for bulk model storage.
- Practical <1 min split: ~15–20s STREAM Triad (RAM) + <5s GPU capacity query/spec lookup (no GPU bandwidth measurement) + ~20–30s fio 4K randread QD32 on a scratch file in the target model directory.

### Prediction model (the math)
- Canonical roofline source: kipply's "Transformer Inference Arithmetic." Compute/memory-bound threshold = hardware_FLOPs ÷ memory_bandwidth (A100 example: 312e12/1.5e12 ≈ 208 — compute is "free" up to a batch-equivalent of 208 tokens). Single-stream decode (batch=1) is always far below this, hence memory-bound. Memory-bound per-token latency: `latency ≈ (2 × params × bytes_per_param) / (N_accelerators × memory_bandwidth)`. https://kipp.ly/transformer-inference-arithmetic/
- **MoE adaptation**: replace total params with *active params per token* (shared/attention params + the routed experts actually selected), not total params. Worked example (Sebastian Raschka): GPT-OSS-20B = 21B total, 4-of-32 experts + shared ≈ 3.6B active/token; on M3 Ultra (~800GB/s unified BW): tok/s ≈ 800 / (3.6 × 2 bytes) ≈ 111 tok/s (bf16). https://sebastianraschka.com/faq/docs/why-moe-huge-params-lower-active-compute.html
- General community-calculator form: `tok/s_ceiling = memory_bandwidth ÷ bytes_moved_per_token`, where `bytes_moved_per_token = (active_params × bytes/param) + KV_cache_bytes_per_token(context_len)`. Real engines land at 50–90% of this ceiling (attention-over-KV-cache overhead, kernel/sampling overhead, growing context). https://martinalderson.com/posts/local-llm-speed-calculator/ , https://joursbleu.github.io/llm-perf-model/
- KV-cache term is architecture-sensitive, not a flat heuristic: Llama-3-70B fp16 KV ≈320KB/token, Mistral-7B ≈64KB/token (halve for fp8); GQA/MLA shrink this sharply vs plain MHA — DeepSeek-V3/R1 specifically use MLA, so a generic per-param KV heuristic will misestimate it. https://martinalderson.com/posts/local-llm-speed-calculator/
- **Prefill/TTFT is compute-bound**, separate model from decode: FLOPs ≈ `2 × active_params × seq_len + attention O(n²)` term; prefill time ≈ FLOPs / (effective_TFLOPS × utilization). Prefill and decode arithmetic intensity differ by 100–500×, which is why they need two separate models, not one "tokens/sec" number. https://arxiv.org/html/2402.16363v3 , https://joursbleu.github.io/llm-perf-model/
- **Mixed VRAM+RAM+SSD offload** (the ktransformers/llama.cpp MoE-split case — not covered by any calculator found, see Prior art): at steady state, decode time/token is dominated by whichever tier's bandwidth gates the slowest resident data actually touched that step — GPU-resident attention+hot-experts from VRAM (consumer GPUs ~500GB/s–1.5TB/s) vs CPU-resident cold-experts from system RAM (~35–75GB/s real-world dual/quad-channel DDR5, i.e. the 70–90%-of-theoretical figure above). SSD read speed mainly gates one-time model-load time, not steady-state tok/s — it only re-enters the per-token critical path if RAM capacity is also insufficient and the OS pages/mmaps hit disk repeatedly.
  - **CORRECTION 2026-08-02 (later wins).** The sentence above is **false for streaming-MoE engines**, which are now a mainstream lane (WASTE, ds4/DwarfStar). When the container exceeds RAM by design, SSD is *the* steady-state budget, not a load-time cost: **54.8% of a Kimi-K3 decode step is expert I/O** — reads are ~2× the arithmetic — and the storage *enclosure* becomes the ceiling (internal NVMe ~12.8 GB/s vs external USB bridge ~0.94 GB/s decides whether streaming is viable at all). Evidence + caveats: `waste-engine-verified.md`. Consequence for the predictor: the mixed-tier model needs a real SSD-bandwidth term and a `regime ∈ {gpu, disk, hybrid}` branch — in the disk regime the 4K-random-read probe stops being a nice-to-have and becomes the gating input.
  - PCIe transfer term = bytes moved GPU↔CPU per decode step ÷ achieved PCIe bandwidth. Consumer PCIe Gen4 x16 ≈32GB/s theoretical, Gen5 x16 ≈64GB/s theoretical, with reported GPU→CPU/CPU→GPU asymmetry (~22GB/s vs ~15GB/s on Gen5 in one source). In practice this is usually a secondary correction, not the dominant term, for typical batch-1 MoE offload — RAM/VRAM bandwidth dominates over PCIe transfer at consumer batch sizes. https://servermall.com/blog/pcie-gen4-gen5-bandwidth-and-bottlenecks/ , https://gigagpu.com/pcie-bandwidth-multi-gpu-inference/
- Calibration data points for validating any predictive model against real ktransformers/llama.cpp runs: DeepSeek-V2-Chat, llama.cpp on 2×RTX3090 (48GB, 95% VRAM used) ≈7.5 tok/s vs ktransformers ≈9 tok/s at only 45% VRAM used; ktransformers claims up to 28× faster prefill / 3× faster decode vs llama.cpp (vendor claim, hardware/quant/config-dependent, not independently reproduced in sources found). https://www.noze.it/en/insights/ktransformers-hybrid-cpu-gpu-inference/ ; DeepSeek-V3 on ktransformers, 4×RTX4090 (~80GB total VRAM) ≈3.7 it/s. https://www.pugetsystems.com/labs/hpc/exploring-hybrid-cpu-gpu-llm-inference/

### Prior art (existing estimators + accuracy)
- **Decode-speed calculators** (bandwidth-ceiling model, client-side JS, no real execution):
  - Martin Alderson's Local LLM Speed Calculator — explicit `bandwidth ÷ bytes/token`, self-labeled "an optimistic upper bound," cites real engines (llama.cpp/MLX/vLLM) hitting 60–90% of ceiling. https://martinalderson.com/posts/local-llm-speed-calculator/
  - joursbleu LLM Performance Model (Prefill & Decode Estimator) — separate FLOPs-based prefill + bandwidth-based decode models, browser-only, self-labeled "theoretical upper bounds." https://joursbleu.github.io/llm-perf-model/
  - InventiveHQ LLM Inference Speed Calculator (page 403'd on fetch; WebSearch snippet corroborates same bandwidth/bytes-per-token approach) https://inventivehq.com/tools/developer/llm-inference-speed-calculator ; techfuelhq Local LLM Speed Calculator, same category. https://techfuelhq.com/tools/llm-speed-calculator/
- **Capacity-only calculators** (answer "does it fit," not "how fast"): HF Space "LLM Model VRAM Calculator" (NyxKrage) https://huggingface.co/spaces/NyxKrage/LLM-Model-VRAM-Calculator ; apxml "Can You Run This LLM?" (Nvidia + Apple Silicon) https://apxml.com/tools/vram-calculator ; CanItRun.dev, Spheron GPU Recommender, TitaniumMonkey LLM_Hardware_Calculator (pulls live HF model metadata: https://github.com/TitaniumMonkey/LLM_Hardware_Calculator).
- Reported accuracy for the VRAM-only category (secondary aggregator source, lower confidence — no primary methodology/validation page found): "70–85%" typical, "90–95%" for best tools when properly configured; real usage often exceeds estimate by 20–30%. Named error sources: KV-cache/activation/overhead lumped into a flat 20% markup (wrong across model sizes since the three terms scale differently); quantization bytes/param mis-modeled (naive 0.5 B/param for "4-bit" vs real GPTQ/AWQ INT4 ≈0.52–0.55, GGUF Q4_K_M ≈0.61 B/param / 4.9 effective bits). https://www.propelrc.com/llm-vram-calculator/ (secondary, directional only)
- **Gap confirmed**: no tokens/sec calculator found that (a) is validated against a public benchmark suite with reported error bars, or (b) models the specific mixed VRAM+RAM+SSD MoE-offload split (llama.cpp `--n-cpu-moe`/`--override-tensor`, ktransformers kt-kernel expert-placement — see linked node). Every calculator found assumes the model is fully in VRAM, fully in unified memory (Apple), or fully in RAM; none combine tiers with a PCIe-transfer correction term. This is the gap this project's preflight tool would fill.
- Neither ktransformers nor llama.cpp ships a pre-download speed predictor. llama.cpp's `llama-fit-params` (PR #16653, discussion https://github.com/ggml-org/llama.cpp/discussions/18049) estimates memory fit/split for a model already on disk, not pre-download speed, and per the linked node has open correctness bugs (Windows overflow, non-authoritative failure handling).

## Open questions
- No independently verified error bars (MAE/RMSE vs measured tok/s) found for any bandwidth-ceiling calculator — every one self-reports as a "theoretical/optimistic upper bound" with no published validation study across multiple GPU/RAM configs.
- Whether a one-time <1 min install-time probe (STREAM/fio) stays representative over time — thermal throttling, background load, NUMA placement on multi-socket, XMP/EXPO profile not enabled by default — no source addresses probe staleness/drift.
- No public data found on real-world "effective bandwidth utilization %" specific to ktransformers' CPU-expert-offload path (vs. the generic 50–90% cited for plain dense-model GPU/CPU inference) — needed to calibrate a MoE-offload-specific model rather than reusing the dense-model figure.
- PCIe GPU↔CPU asymmetry and NUMA cross-socket penalties are both real per sources found but neither appears inside any existing tok/s prediction formula located — would have to be added as unvalidated correction terms.
