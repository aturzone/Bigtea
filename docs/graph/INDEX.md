- research/ring-wraparound-2026-08-11.md — **DONE, the 256-token V4-Flash cap is gone (#46).** Raw KV latents were `kv_lora_rank * 256` **indexed by absolute position**, so position 256 wrote past the end; they now live in a 1024-slot ring and the compressed half grows. **A ring is exact only because raw attention is *sliding*** — the container declares `attention.sliding_window = 128`, so a position older than the window can never be read again; `sliding_window = 0` is refused rather than silently dropping visible keys. **The compressed half cannot be a ring at all**: it is visibility-limited, not windowed, so every complete block behind a token stays reachable — two structures, two reasons, and treating them alike either caps the context or wastes memory. The size is the **window plus the batch**, not the window: a pass's earliest query reaches `window - 1` behind `pos0`, and measuring from the last query would drop exactly the keys the first rows of a prefill need. The mask was rewritten with the ring, as the cache's own comment predicted it would have to be — the key axis is a gathered run of absolute positions, not slot order. Only limit left is 897 tokens per pass. Verified past the cap with the R3 equivalence harness (argmax agrees, 0.373% apart). **Left stale on purpose: `bigtea-serve.rs` still reports a 256 context limit** — links: backlog/r3-kv-cache.md, v4flash-compressed-attention.md
- research/r2-overlap-2026-08-11.md — **BUILT AND MEASURED, 1.07x prefill / 1.13x generation, ON by default.** Block N+1's always-read weights are read while block N computes. Exact, not speculative: routing is data-dependent so N+1's *experts* cannot be known, but its **dense** tensors do not depend on routing at all. **The dense read is now free — 2.15s to 0.02s over 86 block-passes** — but the expert reads gave 1.16s of it back, which is why this is a third of the ~1.4x ceiling and not all of it. **The toll is the drive, not the pool split**: 2 prefetch handles hide the dense read as completely as 4, and 4 cost the experts no more than 2, so both sets of reads are simply competing for the same bandwidth. Handled first: `read_range_into_via` needs *distinct* slots and `read_expert_slices` already used all eight, so a naive prefetch would have reintroduced by hand the queue-depth-1 bug that was worth 1.32x. **Off entirely when residency is satisfied** rather than merely idle, since shrinking the foreground pool to feed a thread that reads nothing is a pure loss. Free RAM matched to 0.03 GiB across all runs — links: backlog/r2-overlap-reads-with-compute.md, the-plateau-was-ours-2026-08-10.md
- research/gbnf-grammars-2026-08-11.md — **BUILT AND VERIFIED AGAINST llama.cpp.** `crates/bigtea-grammar` (no dependencies at all — not ggml, not the tokenizer) parses GBNF, compiles it to a stack matcher, and turns the bytes so far into the token ids that may legally come next; unlocks `--grammar`, `--grammar-file`, `--json-schema`, `--json-schema-file`. **A grammar that accepts everything passes any test that only checks acceptance**, so the accepted text is llama.cpp's own output under the same grammar at `--temp 0` and every case also checks a one-character-edit rejection. Everything unimplemented is refused **by name**, because ignoring a schema keyword yields a grammar looser than asked for and nothing downstream can tell. **Library only — not wired into the CLI**, which another session owns — links: backlog/llamacpp-flag-audit.md, backlog/lts-parity-criteria.md
- research/v4flash-repacking-2026-08-10.md — **MEASURED, a negative and a shipped crash fixed.** Repacking is worth 1.42x on Qwen3-4B prefill and does **not** transfer to V4-Flash: every always-read tensor there with a repackable shape is `Q8_0`, and ggml's repacked `Q8_0` kernels are **NEON and RISC-V only — there is no x86 branch**. - research/the-plateau-was-ours-2026-08-10.md — **MEASURED AND IMPLEMENTED, 1.32x on expert reads.** Two written-down "facts" were ceilings we had built. (1) **The expert matmul is 3% of a token, not the 1.0s floor everyone assumed** — `bigtea-kernelbench` (new) times it with weights already in RAM: 3.02 ms/block at **24.7 GiB/s, above single-threaded memcpy**, i.e. already at DRAM speed. **76% of a token is disk.** It also shows compute scales as ~`n^0.49` in the batch, not linearly, which *corrects the speculative-decoding pessimism* in the no-slack node. (2) **The "no gain past 4 readers, the drive does 2.37 GiB/s" plateau was a synchronous-handle artefact** — all four readers shared one `DirectFile`, and a Windows handle without `FILE_FLAG_OVERLAPPED` is serialised by the OS, holding the drive at queue depth 1. `bigtea-iobench` (new), identical reads, one variable: **2.01 GiB/s shared vs 2.65 per-handle at 4 threads**, and per-handle beats the recorded "sequential ceiling". Implemented as an 8-handle pool per shard plus `prefetch_dense`; expert reads 2.03 → **1.54 s (1.32x, matching the bench's prediction)**, dense re-reads 1.39x per GiB. End-to-end rows are flagged as *not* a clean A/B (residency differed) — normalised, 1.19x. Revises the machine's ceiling to ~**0.65 tok/s vs llama.cpp's 0.39** once R2 lands — links: v4flash-has-no-slack-2026-08-10.md, zero-copy-expert-reads.md, backlog/the-big-bang.md
- research/v4flash-has-no-slack-2026-08-10.md — **MEASURED, three negatives that close the byte-reduction roadmap.** (1) **The expert bank is full-rank**: `bigtea-spectrum` (new, needs no forward pass) asked whether all 256 experts in a layer share a subspace — a rank-512 basis holds **20.4%** of the bank's energy against **16.6%** for matched noise, i.e. 1.23x from nothing; confirmed on two layers and two projections, converged, and conservative by construction. (2) **The router's tail is not small**: renormalised weights are 33.5/20.6/15.0/12.1/10.1/**8.8**% against 16.7% uniform, so "the 6th expert contributes little" is false and reading 3-of-6 discards 31% of the routing mass. (3) **Speculative decoding is ~1.4x here, not the 2.2x two docs cite** — the verify pass costs *more* bytes than a single-token pass because more tokens select more distinct experts (`U(n)≈6·n^0.667`), and below α≈0.75 it is a net loss. With the earlier 9.1%-negligible result that is four probes and four negatives: **V4-Flash has no redundancy to harvest**, 3.21 GiB/token is what the model costs, and 20 tok/s is not a code problem. Points at the one question this makes answerable and nobody has published — the **tok/s-versus-RAM frontier for a 144 GB model**, which only an engine that owns residency can sweep — links: v4flash-28-tokens-per-second.md, routing-skew-is-per-prompt-2026-08-08.md, backlog/the-big-bang.md

- research/zero-copy-expert-reads.md — **T0.1, resolved.** The "1.06 GiB/s disk" in a V4-Flash prefill was 34-36% memcpy: every expert byte was copied three times (`.to_vec()` in `read_at`, `extend_from_slice` into the stack, `Arc<[u8]>::from` in `bind`). Behind that sat a bigger finding — **GGUF pads tensor data to 32 bytes, not to a sector**, so V4-Flash's experts start at file offset ≡ 2816 (mod 4096) and *no* conventionally-aligned buffer can ever receive a direct transfer. Deliberately skewing the destination by the same 2816 (`SkewedBuf`) makes the residues agree: 0.80 → 1.58 GiB/s with 0.09% of bytes copied, and **1.38x end-to-end on the real model** (32.4s → 23.7s prefill, same token, all 14 forward tests still matching llama.cpp) — links: v4flash-speed-budget.md, ../backlog/lts-0-0-0.md

## backlog/ — one file per epic; small tickets referencing the decision they depend on
- backlog/layernorm-and-biases.md — **SCOPED 2026-08-11, NOT STARTED. The next tier of architectures is blocked on ONE shared feature, not per-model quirks.** StableLM and StarCoder2 were downloaded, run and diagnosed: both emit the qwen2 CJK-noise signature, and both for the same two reasons. **`bigtea-ggml` binds `ggml_rms_norm` and not `ggml_norm`** — LayerNorm subtracts the mean and carries a *bias*, and substituting RMSNorm is not an error, it is that noise; the tell is `attn_norm.bias` in the container, plus the key being `attention.layer_norm_epsilon`. And **there is no bias support anywhere in the dense path** (`grep '\.bias'` over stream.rs/qwen3.rs returns nothing). Two extras: StableLM rotates only **16 of its 64** head dims (`rope.dimension_count = 16`, partial RoPE) and StarCoder2's FFN is **not gated** (no `ffn_gate` — plain MLP with GELU). Worth doing as one feature because LayerNorm+biases is the shared shape of falcon, gpt2, gptneox, bloom, phi2 and starcoder too — links: lts-parity-criteria.md, ../research/gemma3-not-verified-2026-08-11.md

- backlog/r3-kv-cache.md — **READY TO IMPLEMENT: R3 scoped against the code, the critical path.** Names the **three** pieces of state that must persist per layer, not two — raw KV latents (512×256 F16), compressed summaries, and the **compressor input ring** that `deepseek4_forward.rs:698` records llama.cpp keeping and Bigtea skipping because a prefill finds those rows in the current batch. Incremental decode cannot, and `state_rows` is 8 for CSA / 4 for HCA. ~24 MB total; memory is not the problem, silence is. Carries the incremental rules (blocks are 4 positions, so the compressed half updates one step in four), the traps that fail quietly (slot index *is* the absolute position today, so the mask must be rewritten in the same change; RoPE is applied pre-cache at block-start positions), and — the useful correction — **it needs no new llama.cpp oracle**: `prefill` is already verified, so `prefill(0..n) then step(n)` must equal `prefill(0..=n)`, tested at 2, 5 and 165 tokens because each length runs a different attention builder. Worth ~0.25 tok/s from the 4.0s single-token pass alone, i.e. parity, and it is what makes R1 pay — links: next-session-handoff.md, ../research/expert-cache-is-early-not-wrong-2026-08-08.md, ../research/v4flash-compressed-attention.md
- backlog/the-big-bang.md — **PROPOSED, awaiting Atur: what "the best model runner for anyone" has to mean.** Every claim tagged *measured* / *arithmetic* / *unproven*. Kills three appealing pitches outright (larger-than-RAM is not a differentiator — llama.cpp does it; we are not faster; 20 tok/s on a laptop needs a 96.3% hit rate). States the claim that *is* ours: **owned residency** (the kernel's LRU is the worst policy for a cyclic expert scan — 17%→70% measured — and a cache that does not own its memory becomes a page fault in disguise, neither fixable by an mmap engine) plus **honest prediction before a 144 GB download**.
