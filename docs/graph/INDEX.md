- research/zero-copy-expert-reads.md — **T0.1, resolved.** The "1.06 GiB/s disk" in a V4-Flash prefill was 34-36% memcpy: every expert byte was copied three times (`.to_vec()` in `read_at`, `extend_from_slice` into the stack, `Arc<[u8]>::from` in `bind`). Behind that sat a bigger finding — **GGUF pads tensor data to 32 bytes, not to a sector**, so V4-Flash's experts start at file offset ≡ 2816 (mod 4096) and *no* conventionally-aligned buffer can ever receive a direct transfer. Deliberately skewing the destination by the same 2816 (`SkewedBuf`) makes the residues agree: 0.80 → 1.58 GiB/s with 0.09% of bytes copied, and **1.38x end-to-end on the real model** (32.4s → 23.7s prefill, same token, all 14 forward tests still matching llama.cpp) — links: v4flash-speed-budget.md, ../backlog/lts-0-0-0.md

- research/v4flash-generation-first-numbers.md — **the T0 gate, and it FAILED.** V4-Flash generates coherent text on a 15.7 GiB laptop at **0.042 tok/s against llama.cpp's 0.45 — 10.7x slower**; no competitive claim is supportable and none is made. Records why the missing KV cache costs *disk traffic* rather than attention (a 5-token pass touches ~26 expert slices per layer, a cached single-token pass would touch 6), and the re-measured per-phase profile: expert reads 47%, **`layer_tail`+`moe_routing` 21% and unexamined**, dense reads 17%, expert compute 17%, **attention 4%**. Thread count 4→20 changes nothing, so the non-I/O time is not parallel arithmetic and no kernel work addresses it — links: zero-copy-expert-reads.md, head-to-head-llamacpp-2026-08-05.md, ../backlog/lts-0-0-0.md

- research/v4flash-vs-llamacpp-2026-08-07.md — **the V4-Flash head-to-head, and a same-day RETRACTION.** Its first version claimed Bigtea led on load (3.0x) and prefill (1.20x); both were FALSE and shipped to the README and the v0.0.1 release before being caught — Bigtea's numbers were fresh, llama.cpp's were copied from a two-day-old doc, and the engines were never run back to back. Bigtea leads on nothing on this model.** Diagnoses why — llama.cpp overlaps I/O with compute via mmap readahead, Bigtea runs 2.3s of I/O and 1.0s of compute strictly serially — links: verify-before-citing.md, head-to-head-llamacpp-2026-08-05.md

- backlog/roadmap-after-v0.0.1.md — **everything left, ordered by measurement, and the answer to "20 tok/s on this laptop": no.** 20 tok/s = 50 ms/token = 64 GiB/s of expert reads against a 2.37 GiB/s drive — **27x short**, and every byte-reduction lever this project has stacked together is ~8x. Not a hard target, an impossible one. What *is* achievable is beating llama.cpp, and the whole gap is **one architectural difference**: they overlap I/O with compute via mmap readahead, we run 2.3s of I/O and 1.0s of compute serially. T1 overlap (start with layers 0-2, which route by token id and are knowable before any compute), T2 KV cache, T3 residency, T4 fewer bytes (measure routing overlap FIRST), T5 product — links: v4flash-vs-llamacpp-2026-08-07.md, lts-0-0-0.md

- research/expert-cache-is-early-not-wrong-2026-08-08.md — **R1, built and measured: the expert cache is correct and buys nothing yet, so it ships OFF.** Carries the number nobody had measured — expert reads are **deduplicated per block across the batch**, so a pass reads the *distinct* experts its tokens select: **6 at one token (3.21 GiB), 39.7 at 17 tokens (21 GiB), 122.8 at 166 tokens (66 GiB)**. Against that, the ~1.5 GiB this machine can spare returned **1.9-4.1% hits, no generation gain, and a 17% slower prefill** (64.5s → 75.3s) from admission copies — both pairs producing byte-identical text, so the cache is right and the workload is wrong. It inverts once R3 shrinks a step to 6 experts/layer, where R0.1's 86% coverage applies. Also records why frequency must be weighted **by selections not requests** (dedup ties every count on a long prompt and freezes the cache on whatever layer 0 loaded first) — links: routing-prefill-predicts-generation-2026-08-08.md, ../backlog/next-session-handoff.md
- research/routing-prefill-predicts-generation-2026-08-08.md — **R0.1, resolved: the prompt predicts its own continuation, so R1 is worth building.** R0 left R1 undecided by showing the hot set does not transfer *between* prompts (53.7%); this measures the regime a cache is actually in — warm on the prompt, spend on the tokens generated after it. A top-64 set from the prompt alone covers **86.3%** of generated-token routing, within 4.5 points of a 90.8% in-prompt oracle and 33 above cross-prompt. **Continuing to warm during generation adds 0.7 points**, so fill during prefill and leave it. No decay over 15 tokens (first third 82.5% → last third 86.8%). Projected disk floor on the laptop's reachable 4.28 GiB tier: **~1.3 tok/s against llama.cpp's measured 0.21-0.31**. Method turns v0.0.2's artefact into the instrument: passes are kept apart, and because the model is causal `pass[k]-pass[k-1]` is exactly one generated token's routing — asserted, with 0 negative cells and 6.0 selections per layer — links: routing-skew-is-per-prompt-2026-08-08.md, ../backlog/the-big-bang.md
- research/routing-skew-is-per-prompt-2026-08-08.md — **R0, resolved: the skew is real, the hot set is not.** Eight prompts over four subjects (incl. a Persian *coding* prompt, so subject and language are crossed), layers 0-2 excluded, one prefill each. The skew survives — top-8 takes 5-7x a uniform router at the same sample size, on every prompt. What dies is transfer: a top-64 set pinned from one prompt covers **61.3%** of another on the same subject, **37.5%** across subjects, against **25.0%** for a random cache — and the noise ceiling is 88.7%, so that collapse is real divergence, not a small sample. Corrects four v0.0.2 figures: top-64 97.8% → **90.5% in-sample / 53.7% out**, the 34.27 GiB **33.6 tok/s floor → 1.60**, "20 tok/s on a ~48 GiB desktop" → unsupported (needs 96.3% hits; pinned gives 76.7% at 68.5 GiB), and chi-square 7805 → **not a valid statistic**, since stateless regeneration re-counts the prompt per token (1282 → 5464 → 11469 for 1/4/8 passes, coverage unmoved). Kills the handoff's "prune the model to its hot set" item and reshapes R1 to warm-not-pin — links: routing-skew-changes-everything.md, ../backlog/next-session-handoff.md, verify-before-citing.md
- research/routing-skew-changes-everything.md — **⚠ SUPERSEDED by routing-skew-is-per-prompt-2026-08-08.md; has a 2026-08-08 CORRECTION BLOCK at top — read it before citing any number here.** **the assumption under every speed estimate in this project was wrong.** V4-Flash's router is violently skewed: **one expert of 256 absorbs 12.1% of selections, and 64 of them (25% of the model) absorb 97.8%** — chi-square 7805 against uniform's ~255. ## backlog/ — one file per epic; small tickets referencing the decision they depend on
- backlog/r3-kv-cache.md — **READY TO IMPLEMENT: R3 scoped against the code, the critical path.** Names the **three** pieces of state that must persist per layer, not two — raw KV latents (512×256 F16), compressed summaries, and the **compressor input ring** that `deepseek4_forward.rs:698` records llama.cpp keeping and Bigtea skipping because a prefill finds those rows in the current batch. Incremental decode cannot, and `state_rows` is 8 for CSA / 4 for HCA. ~24 MB total; memory is not the problem, silence is. Carries the incremental rules (blocks are 4 positions, so the compressed half updates one step in four), the traps that fail quietly (slot index *is* the absolute position today, so the mask must be rewritten in the same change; RoPE is applied pre-cache at block-start positions), and — the useful correction — **it needs no new llama.cpp oracle**: `prefill` is already verified, so `prefill(0..n) then step(n)` must equal `prefill(0..=n)`, tested at 2, 5 and 165 tokens because each length runs a different attention builder. Worth ~0.25 tok/s from the 4.0s single-token pass alone, i.e. parity, and it is what makes R1 pay — links: next-session-handoff.md, ../research/expert-cache-is-early-not-wrong-2026-08-08.md, ../research/v4flash-compressed-attention.md
